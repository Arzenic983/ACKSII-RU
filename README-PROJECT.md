# ACKS II на русском языке — руководство по проекту

Этот репозиторий — общая рабочая папка перевода **Adventurer Conqueror King System II**. Он предназначен для переводчиков, редакторов и ИИ-агентов: здесь находятся английские источники, русский Markdown, словарь, база единиц перевода и материалы проверок.

Репозиторий: **[Arzenic983/ACKSII-RU](https://github.com/Arzenic983/ACKSII-RU)**. Доступ приватный; владелец и координатор — **Arzenic983**. Инструкция описывает состояние на **18 октября 2026 года**. Последующий прогресс проверяйте по файлам и истории коммитов.

## Быстрый старт

1. Получите приглашение от владельца, сообщив ему свой GitHub-логин, и примите его.
2. Установите Git и Git LFS. Для чтения и редактирования `.md` достаточно редактора с поддержкой Markdown, например VS Code или Obsidian. Python нужен для базы и обмена переводами; Node.js — только для повторной сборки читательского файла.
3. Клонируйте репозиторий командами ниже.
4. Прочитайте [глоссарий](ACKSII/Глоссарий.md), [правила двуязычного оформления](<ACKSII/База перевода/bilingual_style.md>) и отчёт по своей главе.
5. Согласуйте главу или диапазон страниц с координатором. В одной задаче указывайте книгу, главу, страницы и вид работы: перевод, вычитка, терминология или сборка.
6. Работайте в отдельной ветке и передавайте результат через Pull Request (PR, запрос на включение изменений).

### Полное клонирование

Команды работают в PowerShell и обычном терминале Linux/macOS:

```sh
git lfs install
git clone https://github.com/Arzenic983/ACKSII-RU.git
cd ACKSII-RU
git lfs pull
git switch -c codex/ch03-translation
```

В GitHub Desktop можно использовать тот же адрес репозитория. Для работы с приватным проектом потребуется вход в приглашённый аккаунт GitHub. Пароль аккаунта не вставляйте в адрес репозитория или в файлы проекта.

Если после скачивания Git сообщил `active post-checkout hook found during git clone`, проверьте `git status` в созданной папке. Такая ошибка встретилась при проверке проекта на Git 2.45.1 для Windows со стандартным hook Git LFS. В **свежей копии без собственных правок** завершить восстановление файлов и загрузку LFS можно так:

```sh
git restore --source=HEAD --worktree -- .
git lfs pull
```

`git restore` заменяет файлы состоянием из `HEAD`, поэтому этот способ предназначен только для новой копии. Проверка проекта выполнена без отключения защиты клонирования Git.

В проект входят крупные книги, архивы FoundryVTT, изображения и SQLite. Полное клонирование скачивает также эти материалы. Они находятся в **Git LFS**. Если вместо PDF или базы виден короткий текст `version https://git-lfs.github.com/spec/v1`, установите LFS и выполните `git lfs pull`. Скачивание ZIP со страницы GitHub не заменяет этот процесс.

### Клонирование только рабочих материалов

Markdown и JSON доступны без скачивания всех архивов. Для начала в PowerShell:

```powershell
git lfs install
$env:GIT_LFS_SKIP_SMUDGE = '1'
git clone https://github.com/Arzenic983/ACKSII-RU.git
Remove-Item Env:GIT_LFS_SKIP_SMUDGE
cd ACKSII-RU
git lfs pull --include="ACKSII/База перевода/acksii_translation.sqlite,ACKSII/Source/ACKSII Revised Rulebook.pdf"
```

В Linux/macOS используйте `GIT_LFS_SKIP_SMUDGE=1 git clone https://github.com/Arzenic983/ACKSII-RU.git`, затем `cd ACKSII-RU` и ту же команду `git lfs pull --include=…`. Для работы только с Markdown можно пока не скачивать базу и PDF. Не открывайте и не сохраняйте LFS-указатель как настоящий двоичный файл.

## Источник, термины и точность перевода

Основной подготовленный английский источник — [ACKSII Revised Rulebook (EN checked).md](<ACKSII/Source/ACKSII Revised Rulebook (EN checked).md>). Если извлечённый текст выглядит повреждённым, сверяйтесь с соответствующей страницей PDF. `RAW TEXT DUMP` — первоначальное извлечение; при расхождениях оно не заменяет проверенный текст и PDF.

`pdf_page` — физическая страница PDF, начиная с 1, включая обложку. `printed_page` — номер, напечатанный в книге. Они различаются. Внутренние ссылки на страницы книги сохраняют номера оригинала.

Единицы имеют постоянные идентификаторы: `rr.p0015.b003` — текстовый блок, `rr.p0019.t01.r002.c02` — ячейка таблицы. Сохраняйте комментарии `<!-- unit: … -->`, якоря, порядок строк и столбцов, `rowspan`/`colspan` и авторские сноски. HTML-таблицы в Markdown нужны для объединённых ячеек; не превращайте их автоматически в простые таблицы.

Перевод должен точно передавать механику игры. Проверяйте числа, знаки модификаторов, проценты, `d6`/`d20`, ограничения, исключения и ссылки. Сохраняйте исходные футы, мили, фунты и стоуны. Ошибки и противоречия оригинала отмечайте звёздочкой и пояснением рядом с текстом; не подставляйте догадку как установленное правило.

**Правило владельца о конфликтах, уточнённое 16 октября 2026 года:** если сведения перевода противоречат друг другу, найдите соответствующие английские места **обеих затронутых глав**; при разночтении таблицы и описания проверьте оба места оригинала. Если конфликт внесён переводом, исправьте его по оригиналу и добавьте пометку, что исправлена ошибка перевода. Согласуйте исправление в полной главе, пакете для базы и общем читательском файле. Если противоречит себе сам оригинал, сохраните обе исходные формулировки и числа и объясните разночтение под звёздочкой рядом с текстом; приведите страницы и ID. Не устраняйте авторский конфликт догадкой и не называйте конфликтом оригинала непроверенную ошибку перевода.

Терминологию сверяйте с [глоссарием](ACKSII/Глоссарий.md), [glossary.json](<ACKSII/База перевода/glossary.json>) и контекстом. Утверждённые «Природоведение», «Мифография», «Особый урон» сохраняются. Не смешивайте **КБ = AC**, **КЗ = HD**, **ОЗ = hp**. У одного английского слова могут быть разные значения: например, Venturer как класс и Venturers в разделе НПС.

Новые названия и спорные исправления предлагайте с английским оригиналом, страницей и объяснением. В базе `working_labels` и в [bilingual_terms.md](<ACKSII/База перевода/bilingual_terms.md>) есть рабочие варианты: они не означают утверждения словаря. В [review.md](<ACKSII/База перевода/review.md>), [02_review.md](<ACKSII/База перевода/02_review.md>), [03_review.md](<ACKSII/База перевода/03_review.md>) и [04_review.md](<ACKSII/База перевода/04_review.md>), [05_review.md](<ACKSII/База перевода/05_review.md>) перечислены известные разночтения. В старых разделах отчётов учитывайте дату и последующие уточнения.

### Двуязычное оформление

Следуйте [bilingual_style.md](<ACKSII/База перевода/bilingual_style.md>):

- При **каждом** употреблении специального или неоднозначного термина добавляйте английское имя: `Мифография [Loremastery]`, `Мифографией [Loremastery]`.
- Под русским заголовком отдельной строкой ставьте `<small>ENGLISH HEADING</small>`; в заголовках таблиц — английскую строку после `<br>`.
- Сохраняйте английские подписи в таблицах и редакторских примечаниях; избегайте вложенных квадратных скобок.
- Комментарии к правилам и вопросам перевода должны оставаться рядом с соответствующим текстом, в том числе в компактной копии.

В SQLite хранится русский перевод **без оформительских английских вставок**. Двуязычные подписи добавляются в представление Markdown. Поэтому буквальное несовпадение этих двух форматов само по себе не означает потерю перевода.

**Постоянное пожелание владельца, повторно подтверждённое при поручении главы 3:** продолжайте оформление читательского файла глав 1–2 во всех следующих главах. Образец на фотографии задаёт расположение заголовков: русский заголовок сверху, оригинальный английский — непосредственно под ним отдельной строкой меньшего размера. В Markdown это `### Русский заголовок`, пустая строка и `<small>ORIGINAL ENGLISH HEADING</small>`; уровень `#` выбирается по структуре раздела. Английские названия специальных и неоднозначных терминов в квадратных скобках повторяются **при каждом употреблении**, включая таблицы и примечания. Падеж меняется у русского текста; английская подпись остаётся названием соответствующего термина. Эти требования действуют без нового напоминания в каждом запросе.

Законченную главу сначала сверяйте с источником, глоссарием, числами и таблицами, затем добавляйте в общий читательский файл. Сохраняйте отдельную полную главу, пакет с постоянными ID и исходной `revision`, а также все содержательные примечания рядом с текстом. При расширении общего документа обновляйте диапазон в имени файла и ссылки на него. Цвета и конкретный шрифт зависят от Markdown-просмотрщика; в исходном Markdown сохраняются двуязычная структура и относительный размер английской строки.

## Работа переводчика и редактора

**Уточнение владельца от 16 октября 2026 года:** при переводе каждой следующей главы обязательно сверяйте специальные термины с `ACKSII/Глоссарий.md`, `glossary.json` и `bilingual_terms.md`. Повторяйте сверку перед завершением главы и отмечайте её фактический результат в отчёте. При расхождении словаря и рабочего перевода сохраняйте утверждённый словарный вариант; спорное новое значение описывайте рядом с текстом и в отчёте, без молчаливой замены термина.

Для небольшого исправления достаточно изменить полную главу и указать в PR идентификатор, оригинал, новую формулировку и причину. Если меняется смысловой русский текст, приложите пакет CSV/JSONL или явно перечислите исправления по ID для интегратора. Для целой главы предпочтителен пакет с сохранёнными номерами редакций.

Из корня проекта выгрузите свою главу; Python **3.10+** со стандартной библиотекой SQLite/FTS5 достаточен:

```sh
python tools/export_chapter.py --chapter 03 --out contributions/03/translator.csv
```

Вместо CSV можно указать `translator.jsonl`. Скрипт читает текущую SQLite-базу, выбирает только одну главу, сохраняет `revision` и SHA-256 исходника и не перезаписывает существующий файл. Для непереведённых строк в пакете уже установлен статус `draft`. Команды с `python` на Windows могут потребовать `py`, а в Linux/macOS — `python3`.

При редактировании пакета:

- Меняйте `russian`, `note` и при необходимости `status`.
- Оставляйте `id`, `chapter_id`, `english`, `source_sha256` и `revision` неизменными. Не присваивайте номер следующей редакции вручную.
- Для перевода ставьте `draft`; после вычитки — `reviewed`. `user_approved` используется только после явного утверждения человеком.
- CSV сохраняйте как **UTF-8 с BOM**, разделитель **`;`**. При импорте в Excel задавайте текстовый тип столбцов, чтобы сохранить обозначения костей, формулы, знаки и номера буквально.
- Не используйте всю книгу в одном пакете: импорт принимает одну главу. При разделении главы между участниками распределяйте непересекающиеся ID.

Добавьте в PR изменённый Markdown, пакет и краткое описание: диапазон, проверенные таблицы и числа, новые термины, оставшиеся вопросы. Перед отправкой просмотрите `git diff` и `git status`.

## Совместная работа через GitHub

Один участник отвечает за согласованный диапазон. Задачу можно зафиксировать в Issue, указав книгу, главу, страницы и ответственного. Для каждого самостоятельного изменения создавайте ветку, например `codex/ch03-translation` или `codex/ch02-terminology`.

Перед началом следующей задачи получите принятые изменения:

```sh
git switch main
git pull --ff-only
git switch -c codex/ch03-review
```

Команды предполагают чистую рабочую папку: текущую работу сначала сохраните отдельным коммитом. В своей ветке добавляйте только файлы задачи, создайте коммит и отправьте ветку:

```sh
git add "ACKSII/Перевод Markdown/03 Навыки.md" contributions/03/translator.csv
git commit -m "Перевести главу 3: Навыки"
git push -u origin codex/ch03-translation
```

В примере отправляйте фактическое имя своей ветки, затем откройте PR в `main`. Координатор проверяет изменения и интегрирует их. Ссылку на задачу, способ проверки и спорные места укажите в описании PR. Переименование файлов и массовое переформатирование выносите в отдельные согласованные изменения, чтобы не затруднять сверку перевода.

**SQLite — единый снимок состояния. Два изменённых файла `.sqlite` из разных веток автоматически не объединяются.** Переводчики передают текстовые пакеты; интегратор последовательно импортирует их в свежую базу. При конфликте `revision` выгрузите актуальные строки и перенесите свою правку с повторной сверкой. Не обходите конфликт простой подменой номера редакции. Не используйте `push --force` для общей ветки.

## Работа интегратора с базой

Подробное описание: [ACKSII/База перевода/README.md](<ACKSII/База перевода/README.md>). Команды ниже выполняются **из корня репозитория**:

```sh
python "ACKSII/База перевода/database_tools.py" verify
python "ACKSII/База перевода/database_tools.py" progress
python "ACKSII/База перевода/database_tools.py" search 'Природоведение'
```

Перед импортом сохраните снимок базы. Закрытую SQLite-базу можно скопировать как файл; для открытой используйте SQLite Backup API. Импорт:

```sh
python "ACKSII/База перевода/database_tools.py" import-chapter contributions/03/translator.csv --chapter 03 --reviewer GitHubLogin
python "ACKSII/База перевода/database_tools.py" verify
python "ACKSII/База перевода/database_tools.py" export
```

Импорт проверяет главу, исходный английский текст, его SHA-256 и ожидаемую `revision`. Любая ошибка отклоняет пакет целиком. Старые редакции сохраняются, пустой русский текст не удаляет существующий перевод. Изменение помечает главу `in_progress`; импорт не означает завершённой смысловой вычитки.

`export` обновляет `units.jsonl`, `glossary.json`, `progress.json` и CSV всех глав, в которых появился перевод. Он **не собирает Markdown** и не обновляет отчёты о смысловой проверке. После импорта согласуйте русский текст полной главы с базой, сохраняя английские подписи и примечания в Markdown. Затем обновите производную читательскую копию и приложите фактические результаты проверок.

На момент создания репозитория в базе есть CSV начала и главы 1; CSV главы 2 ранее не создавался. Получить свежий пакет любой главы можно `tools/export_chapter.py`. Не пересоздавайте SQLite из `schema.sql` поверх текущего файла: схема не содержит перевод и историю.

## Что проверять перед передачей

- Смысл русского текста сверяется с английским источником и, при сомнении, с PDF.
- Числа, формулы, единицы измерения, страницы и геометрия таблиц сохранены.
- Термины и английские подписи согласованы со словарём и правилами оформления.
- Все вопросы и редакторские комментарии остались рядом с текстом.
- Полная глава, пакет для базы и читательская копия отражают один набор смысловых правок.
- Если менялась база, `verify` проходит; если выполнялась сборка, её проверки проходят.
- В PR перечислены реальные проверки и нерешённые вопросы; статус утверждения не приписан автоматически.

Текущие отчёты находятся в `ACKSII/База перевода/`: `validation.json`, `02_validation.json`, `03_validation.json`, `04_validation.json`, `05_validation.json`, `06_validation.json`, `07_validation.json`, `workflow_validation.json`, `bilingual_validation.json` и `reading_validation.json`. Отчёты относятся к конкретному состоянию файлов. Проверки глав 1–2 и прежнего двуязычного оформления описывают свои исторические диапазоны. Полная компактная копия имеет 546 маркеров PDF-страниц; для неё ориентируйтесь на `reading_validation.json` и `full_book_validation.json`, для приложения E — на `E_validation.json`.
